# Features: what a crate should do and doesn't yet

IDs FEAT-1 to FEAT-17 (FEAT-13 is on `master`, from S0 slice 1a); the next new one is **FEAT-18**. Format and
rules: `README.md`.

FEAT-1 to FEAT-4 are each a sheaf entry's crate half: what a crate here offers so sheaf can fix its entry.
The other half (the dialog, the command, the app) is sheaf's and stays in sheaf's entry. FEAT-5 on came from
the prior-art survey (`research/prior-art/README.md`, 2026-11-08).

## For S1 (pages)

- **FEAT-1** · scan-image · S1 · open — **A file's page count from its headers, without decoding.** sheaf's Combine dialog decodes every image in full to show its page count, and G4-encodes the black-and-white ones, so a folder of large scans is slow to list. The crate offers M5 slice 1's `count_frames` (a TIFF's images counted from its headers) and says every other format is one page. The dialog's change is sheaf's. *(sheaf B17)*
- **FEAT-8** · scan-fixtures · S1 · open — **Color and Photo-profile degradations.** Today's `Degradation` steps are gray only, so the Photo profile's color steps (shadows, color casts, paper whitening, page finding) can't be tested on seeded pages. Port selected effects from Augraphy (MIT; Python, slow, no documented seeding): LightingGradient, ShadowCast, ColorPaper, PageBorder (feeder borders), BleedThrough, punch holes, perspective and curl, on the fixtures' own generator. No Rust library degrades document images. *(survey, page cleanup and fixtures)*

## For S2 (PDF)

- **FEAT-2** · pdf-scan · S2 · open — **Pages written one at a time, each image dropped once it's written.** sheaf's images-to-pdf reads every image before writing anything: black and white pages are G4 bytes, but gray and color pages are held as pixels, about 2.5 GB for 100 color Letter pages at 300 dpi. `pdf-scan` writes a page at a time through `write::Parts` (`crates/pdf-scan.md`), and S2 slice 2's memory check holds it. images-to-pdf moving onto it, or onto the intake with no cleanup step, is sheaf's. *(sheaf B18)*
- **FEAT-3** · pdf-scan · S2 · open — **The document's `/Info` from the caller: `/Producer` and `/CreationDate`.** sheaf's images-to-pdf and scan outputs have no `/Info`, taking it from an empty primary (`qpdf --show-object=trailer` gives `<< /Root 3 0 R /Size 7 >>`). `pdf-scan`'s document options take the producer and the creation date from the caller, and the crate need read no clock, so the same inputs still make the same bytes (`crates/pdf-scan.md`). sheaf's fix for its own sessions (B8's `Session::new_titled`) is sheaf's. *(sheaf B30)*

## For S0 (scan devices)

- **FEAT-5** · scan-device · S0 · open — **Patch codes the driver reports, as hints beside pixel reading.** TWAIN 2.5 defines `ICAP_PATCHCODEDETECTIONENABLED` and the other `ICAP_PATCHCODE*` capabilities (0x113f–0x1145), a per-image `TWEI_PATCHCODE` (0x1212, values `TWPCH_*`), and job separation through `CAP_JOBCONTROL` with the patch in `TWEJ_PATCH*`. WIA 2.0 has a Patch Code Reader item (`WIA_IPS_PATCH_CODE_READER`, off by default; types 1, 2, 3, 4, 6, T and custom; results as XML or raw). SANE exposes nothing (the fujitsu and kodak backends define fields they never use). Neither TWAIN nor WIA says which edge a code lies along, so `patch-codes` stays the source of truth and these are hints. Unverified: whether the fi-6130, fi-7160 and fi-8170 report `TWEI_PATCHCODE` through PaperStream IP, and which Windows version added WIA's reader. *(survey, patch codes and barcodes)*
- **FEAT-12** · scan-device (`sane` backend) · S0 · open — **Stored SANE ids that reach `dll`'s own name rules refused before `sane_open`, as `BadId`.** Through `dll`, a name starting `fakeusb:`, `fakeusbdev:` or `fakeusbout:` has SANE replay USB traffic from a file the name gives, or record into one, and a name whose backend part is empty (`:<device>`, or the empty name) opens a device of `dll`'s first backend, the last its `dll.conf` lists, which the id never named (`backend/dll.c`, `sane_open`, at sane-backends' `a113b257`, studied; S0 slice 2's probe N1 and its step 1's repair). No listing gives either, so the `sane` backend refuses them before SANE sees them, with an id not `sane:` and Latin-1 or holding a `NUL`, each as `ScanError::BadId` (S0 slice 2's decisions 20 and 25, its security items 2 and 5, for review); an alias named with a leading `:` is refused too, a limit. An empty name after a backend (`fujitsu:`) and a backend's name alone, each opening that backend's first device, stay allowed: they stay within the backend the id names. Built and checked in slice 5 (the milestone's entry): each refused id answered `BadId` with no `sane_open` called. *(S0 slice 2, decisions 20 and 25)*
- **FEAT-14** · scan-worker · S0 · open — **Windows workers in a Job object that ends them with the app, and a tree kill.** NAPS2's practice (study only) and `crates/scan-worker.md`'s hygiene: each worker assigned to a Job object made with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so the app's end, a crash among them, ends the worker and every process a driver started in it. S0 slice 4 left it out (its decision 22): it takes calls `std` doesn't make, so `unsafe` or a crate, and the crates vetted fall short today: `process-wrap` 10.0.1 (MIT OR Apache-2.0, `rust-analyzer`'s and `watchexec`'s) makes its `std` job without kill-on-close (`make_job_object(handle, false)` in its `src/std/job_object.rs`; only its tokio side's `KillOnDrop` sets it), and `win32job` 2.0.3 (kill-on-close) is on `windows` 0.61, beside the 0.62 the `wia` backend will take. Meanwhile a worker exits at the end of its input and aborts 10 s later should a driver's call hang (an abort Windows Error Reporting may report), and a process a driver started outlives both. On Unix each worker leads a process group of its own already, so a group kill there is this item's other half, should a driver be seen to start processes. Built in slice 9, where Windows drivers are tried, with the 32-bit worker. *(S0 slice 4, decisions 12 and 22, and its dependencies weighed)*
- **FEAT-16** · scan-worker · S0 · open — **A worker's end harmless to an app whatever its `SIGPIPE` disposition.** On Unix a write to a pipe whose reader has gone raises `SIGPIPE`; Rust's runtime leaves it ignored, so the client's write fails and it takes that for the worker's end, but an app that sets the default action back (a command-line program may, for `| head`) dies of a worker that closes its input, or ends, just before the client writes (S0 slice 4's code review: exit 141). Today the docs require the app to keep it ignored, and the client writes nothing to a worker it has found exited (its decision 43). To make it hold: on Linux a pipe write's `SIGPIPE` goes to the writing thread, so a writer thread with it blocked would do, but macOS raises it on the process for a pipe, and `F_SETNOSIGPIPE` has no safe crate API found (`nix` 0.31 has neither it nor `sigpending`); a Unix socket pair as the worker's input would, written with `MSG_NOSIGNAL` (Linux and the BSDs; `std`'s `UnixStream` writes so on the stable Rust here, 1.99, unchecked on 1.89) and `SO_NOSIGPIPE` on macOS (`socket2`'s `set_nosigpipe`, safe), Windows keeping its pipes. Its test needs a process with `SIGPIPE` at its default action, which a Rust test sets only with `unsafe` (named as the test crate's exception) or nightly's `-Zon-broken-pipe`. Before slice 11 freezes the protocol and its transport. *(S0 slice 4, its code review's API finding 1; decision 43)*
- **FEAT-17** · scan-worker · S0 · open — **A stop handle: a worker ended from another thread.** `RemoteDevice`'s calls take `&mut self`, and the settings window is untimed by design (it's the user's), so a driver's window that never closes holds the calling thread until the app ends, and nothing else can end it; the docs say so (S0 slice 4's decision 45). A `Send + Sync` handle taken from the device that kills its worker, the waiting call then answering an error of its own rather than `Crashed`, is additive API. Built with slice 9, where TWAIN's own windows are tried. *(S0 slice 4, its code review's API finding 9; decision 45)*

## Later

- **FEAT-4** · pdf-scan · later · open — **Another tool's text layer found, for a redo.** sheaf F10 wants a redo in Recognize Text: another tool's invisible text taken out (render mode 3: Acrobat's Searchable Image, ocrmypdf, ABBYY, a scanner's own), the visible text kept, sheaf's layer written in its place. `pdf-scan`'s reading side already says whether a page has a text layer (render mode 3 or 7; a `/BaseFont` of `GlyphLessFont` or `Occulta`; an invisible-glyph share of 0.50 or more over a scan, `crates/pdf-scan.md`); this asks where the invisible runs are and whether they lie over the page's one image. Taking them out rewrites the page's streams (M11's machinery, sheaf's or pdf-content-streams'), not this crate's. F10's own questions decide what's found: every mode-3 run, or only those over a page-sized image; words overlapping visible text. *(sheaf F10; survey, pdf images and writing)*
- **FEAT-6** · patch-codes · later · open — **Kodak's perpendicular-bar layout: read it, or say it's not read.** A-61599 has two layouts. The reader handles bars parallel to the leading edge (at least 2 in long, within 3.75 in). The other, bars perpendicular to the edge, at least 0.75 in long, within 2 in of it, is for the i280, 3590C and i600 and the toggle patch only. LEADTOOLS searches both directions. Either read it (the same reader turned) or document it as a non-goal. *(survey, patch codes and barcodes; A-61599)*
- **FEAT-7** · scan-cleanup · later · open — **Leptonica's skew confidence and up/down detection, ported.** Postl's differential line sums give a skew with a confidence, so a page of pictures says "no skew" instead of guessing; measured on a binary image reduced four times, with shear rotation, it's cheaper than today's step. `pixUpDownDetect` and `pixOrientDetect` settle the 180° case word shape can't, without a model (weak beyond Latin text). `pixFindPageForeground` is a candidate for auto-crop. C Leptonica 1.87.0 (BSD-2) is the source; the `leptonica` 0.5.0 Rust port a reading aid only. Each is an output change, so a decision, said. *(survey, page cleanup)*
- **FEAT-9** · scan-cleanup · later · open — **Punch-hole removal and color dropout.** Only commercial SDKs do them, and patents may cover them: punch-hole removal (US8494304), color dropout (US7853074, US7961941), judging blanks across duplex sides (US8724182). Check whether they're in force before building any. *(survey, page cleanup)*
- **FEAT-10** · scan-device · later · open — **Network scanning: eSCL, WSD, or saned.** Not planned: the office's fi-series scan over USB only, and network copiers reach sheaf through WIA and sane-airscan. If ever wanted: an eSCL client ported from OpenPrinting's go-mfp (BSD-2) on `mdns-sd` 0.21.7 (Mopria's specification may be used but never redistributed, and grants no patents; `escl` 0.3.0 is too thin: no 503 retry, no job DELETE, first responder only); a saned client from printscan-sane (PR #20, MIT OR Apache-2.0, never run on real hardware) used and improved upstream; WSD through printscan-wsd. Mock servers: fakescan (Apache-2.0) or go-mfp's virtual device. *(survey, SANE and network scanning)*
- **FEAT-11** · sane-dl · later · open — **An authorization callback, if a backend ever needs one.** `sane_init` is called with none (S0 slice 1's decision 10), so a backend that asks for a username and password gets none, and the standard says the request then fails. SANE may call it from `sane_open`, `sane_control_option` or `sane_start`, on the caller's thread and under its call, with the resource's name and two 128-byte buffers to fill, `NUL`-terminated. It takes no user data, so a Rust closure needs a trampoline over a process-wide slot, which suits `sane-dl`'s one `Sane` per process. Wanted only with a networked backend (the `net` backend to a `saned` that asks; FEAT-10), whose passwords go in plain text or MD5 (the survey), so a trusted network's. *(S0 slice 1, decision 10; the SANE standard, `sane_init`)*
- **FEAT-15** · scan-worker · later · open — **A spare worker kept warm.** `crates/scan-worker.md`'s hygiene names one, optional (NAPS2's practice, study only): a worker started before it's asked for, so an open or a listing doesn't wait on a process's start (on Windows, its loading the DSM too). S0 slice 4 left it out (its decision 34): a SANE open can't use one, since its worker's configuration, the stored id's one-backend `SANE_CONFIG_DIR` in the worker's own directory, is the device's and fixed as the worker starts; a listing, or a TWAIN or WIA open, could. Wanted only if a worker's start is measured to keep the user waiting, which nothing has measured yet. *(S0 slice 4, decision 34; `crates/scan-worker.md`)*
