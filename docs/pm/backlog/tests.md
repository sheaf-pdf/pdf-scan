## For S1 (pages)

- **TEST-4** · scan-image, pdf-images · S1 · open — **The hayro codecs fuzzed through our adapters, and run on their conformance sets.** hayro-ccitt, hayro-jbig2 and hayro-jpeg2000 come from one maintainer, and none is on OSS-Fuzz or has independent conformance results. Fuzz each through the adapter `scan-image` and `pdf-images` call it by; run T.88 Annex K's JBIG2 cases and openjpeg-data; count the corpus's 12-bit and arithmetic-coded JPEGs among the 464 DCT scans (zune-jpeg refuses them); measure an all-safe build's speed with SIMD off on 300 dpi Letter pages. Findings go upstream as UP-5. *(survey, image codecs; pdf images and writing)*
- **TEST-6** · scan-fixtures · S1 · open — **Outside images' licenses, before any is vendored.** zxing-cpp's sample and `falsepositives` sets (the cheapest barcode false-read gate), BarBeR's images, and libtiff's sample images (`fax2d.tif`, `g3test.tif`) for BUG-2. Read each license; vendor only what allows it, else fetch at test time or don't use. *(survey, patch codes and barcodes; image codecs)*

## For S2 (PDF)

- **TEST-1** · pdf-scan · S2 · open — **The text layer's viewer matrix.** Early in S2, before the layer is called done: the layer in PDFium, pdf.js and Poppler (`pdftotext` run as a process), and Preview by hand, for right-to-left words, CJK, combining marks, text beyond the BMP, vertical lines, and a word across a `BT`; selection boxes and copy and paste as well as extraction. It settles Q-2 and Q-3 and checks BUG-6. Also: the cause of OCRmyPDF 17.13's "lost characters" in PDFium-based viewers with glyphless fonts (undescribed in its notes), and whether it touches a font that maps every CID to glyph 1; whether sheaf's separately scaled space avoids OCRmyPDF 17.4's selection running past the words; how pdf.js treats render mode 3 in extraction. veraPDF for `.notdef` (its license unread). *(survey, pdf images and writing; OCRmyPDF 17.x release notes)*

## For S0 (scan devices)

- **TEST-7** · sane-dl · S0 · open — **sane-dl against Homebrew's sane-backends on the macOS runner.** Untried: S0 slice 1 kept it out (its decision 18), so an unknown on a runner couldn't hold the slice; on macOS the tests that need libsane say they skipped. Try `brew install sane-backends` on `macos-latest`, then the tests with `SANE_DL_REQUIRE_LIBSANE=1` through an isolated `ConfigDir` naming `test`. Since S0 slice 1's code review `Sane::load()` tries absolute paths on macOS and no bare name (which dyld would also seek in the working directory, and whose fallback search holds `/usr/local/lib` for old binaries only): `/opt/homebrew/lib/libsane.1.dylib` (Homebrew on Apple silicon, as the runners are), `/usr/local/lib/libsane.1.dylib` (Homebrew on Intel), `/opt/local/lib/libsane.1.dylib` (MacPorts). The item says whether Homebrew installs the library under that name there, and whether `load()` opens it. Also: whether Homebrew's build has the `test` and `pnm` backends, and the header contract against its `sane.h` (`SANE_DL_SANE_H`). *(S0 slice 1, `crates/sane-dl.md`)*

- **TEST-9** · scan-device (`sane` backend), sane-dl · S0 · open — **What only the fi-6130 shows of SANE's names and cancels, by hand in slice 6.** S0 slice 2 answered the seam's two SANE unknowns from the standard, the man pages, the backends' code (studied), the `test` backend and the fake (`crates/scan-device-seam.md`, sections 1 and 7); the rest needs the scanner: its name through `fujitsu` (`<model>:<serial>` when it answers the serial query, else `libusb:<bus>:<device>`), what replugging it, another port and a reboot do to that name, what `sane_open` answers for it once it's unplugged and once it's back (`INVAL` with nothing attached, here), and whether the fallback by backend, vendor and model finds it; whether the feeder has pulled the next sheet in before the page in flight ends, and what `sane_cancel` does to a started batch (`fujitsu.c` sends a halt or a cancel command then, studied); in duplex, a cancel that lands after a front: its back read before the batch ends (the model's sheet in flight), and what a batch ended on a front gives next; and its vendor, model and kind as `sane_get_devices` gives them, byte for byte (Q-4). A row each in slice 6's notes. *(S0 slice 2: the seam note's unknowns)*

- **TEST-10** · scan-device (`sane` backend) · S0 · open — **The stored-id worker's configuration tested without the system's.** S0 slice 2's decisions 18 and 19 start the worker that opens a stored SANE id with a one-backend `ConfigDir` written `Search::BeforeSystem`, so SANE reads the current directory and `/etc/sane.d` after it, the system's `dll.aliases` and the backend's own `.conf` among them; a test never reads `/etc/sane.d`. Slice 5's tests of that worker set `SANE_CONFIG_DIR` to the one-backend directory then a private one standing for the system's (`<one>:<stand-in>`, a value `ConfigDir::value` doesn't give), as the slice's step 1 repair did, and check what it found: an alias whose name names no backend (`Desk scanner`) and one whose prefix names none (`office:scan`) each opening through the stand-in's aliases, each listing 0 devices; a stale id of the directory's backend answering `INVAL` from it (`test:9`), and the fallback's listing giving that backend's devices alone, under the system's aliases (`office:scan` and `Desk scanner` through a directory naming `test`). Since S0 slice 2's code review also: an open then a listing in one process, for an alias whose target is gone (`Desk scanner` through a directory naming none, `office:scan` through one naming `office`), the listing then holding the target's backend (`test:0`: `dll` adds a backend as it opens a name, and lists every one it has added; the code review's probe), so the backend lists before it opens, and its fallback compares each listed name's `backend_of` with the id's and takes only a USB connection's name, never the alias's target. *(S0 slice 2, decisions 18, 19, 28 and 29; its step 1's repair probe and its code review's)*

- **TEST-11** · twain-dsm · S0 · open — **twain-dsm's decoders fuzzed.** A `cargo-fuzz` target (nightly) for each pure decoder a driver's bytes reach: capability containers (`Container::decode`, every container and item type), extended image info answers (`ext_info::parse` and `decode`, inline and from a block), the PE reader; seeded with what the sample source sends. Slice 8 has a fixed-seed random-input test of each in the unit tests (`plan.md`'s rule that decoders are fuzzed), run everywhere, i686 included; this is the coverage-guided pass, for a slice with nightly at hand (the decoders `pub(crate)` until then, so the target reaches them through a `doc(hidden)` entry or lives in the crate). *(S0 slice 8, its plan's review, finding 23)*

- **TEST-12** · scan-device · S0 · open — **`RawImage`'s layout tests on a 32-bit `usize` again, in CI.** The private length check takes the platform's limit as a parameter, so its unit tests take the 32-bit case on any host, and S0 slice 3 ran them on a real 32-bit `usize`, built for `wasm32-wasip1` and run under Node's WASI: once in step 1 (11 passed, the 32-bit branches taken), and again in its code review's fixes, which made the limit `isize::MAX` (25 passed with the fake's units, on a copy of the crate without `rusty-fork`). Since `rusty-fork` became a dev-dependency (slice 3's step 3, for the crash and exit tests), the unit tests no longer build there from the crate as it is: `wait-timeout` 0.2.1, which it pulls, doesn't compile for `wasm32-wasip1` (`E0433`). The cheapest repeat is on Windows, where `rusty-fork` builds: `cargo test -p scan-device --lib --target i686-pc-windows-msvc` in the `twain-dsm` job, which installs that target already, or in slice 9's 32-bit worker job; else `rusty-fork` behind `cfg(not(target_family = "wasm"))`. Wanted by slice 4, whose client decodes every page a worker sends through `RawImage::new`, and before slice 11 freezes the model. *(S0 slice 3, step 3's check)*

- **TEST-13** · scan-device · S0 · open — **S0 slice 3's code on CI's Windows and macOS.** Built and checked on Linux, with clippy for `x86_64-pc-windows-gnu` and `x86_64-apple-darwin`; what only CI shows: the fake's tests there (the crash test's child ending by `0xC0000409` on Windows and `SIGABRT` on macOS, read behind `cfg`; the exit's code 42; the held channel, the hang and the deadlines on slower runners, each bounded at 10 s; the crate docs' example), clippy on `x86_64-pc-windows-msvc` and `aarch64-apple-darwin`, `just clippy`'s and `just doc`'s default-feature lines there, `scan-device-msrv` as CI's job on 1.89, and the gates on `ubuntu-latest`'s SANE with every feature built.
