## For S1 (pages)

- **TEST-4** · scan-image, pdf-images · S1 · open — **The hayro codecs fuzzed through our adapters, and run on their conformance sets.** hayro-ccitt, hayro-jbig2 and hayro-jpeg2000 come from one maintainer, and none is on OSS-Fuzz or has independent conformance results. Fuzz each through the adapter `scan-image` and `pdf-images` call it by; run T.88 Annex K's JBIG2 cases and openjpeg-data; count the corpus's 12-bit and arithmetic-coded JPEGs among the 464 DCT scans (zune-jpeg refuses them); measure an all-safe build's speed with SIMD off on 300 dpi Letter pages. Findings go upstream as UP-5. *(survey, image codecs; pdf images and writing)*
- **TEST-6** · scan-fixtures · S1 · open — **Outside images' licenses, before any is vendored.** zxing-cpp's sample and `falsepositives` sets (the cheapest barcode false-read gate), BarBeR's images, and libtiff's sample images (`fax2d.tif`, `g3test.tif`) for BUG-2. Read each license; vendor only what allows it, else fetch at test time or don't use. *(survey, patch codes and barcodes; image codecs)*

## For S2 (PDF)

- **TEST-1** · pdf-scan · S2 · open — **The text layer's viewer matrix.** Early in S2, before the layer is called done: the layer in PDFium, pdf.js and Poppler (`pdftotext` run as a process), and Preview by hand, for right-to-left words, CJK, combining marks, text beyond the BMP, vertical lines, and a word across a `BT`; selection boxes and copy and paste as well as extraction. It settles Q-2 and Q-3 and checks BUG-6. Also: the cause of OCRmyPDF 17.13's "lost characters" in PDFium-based viewers with glyphless fonts (undescribed in its notes), and whether it touches a font that maps every CID to glyph 1; whether sheaf's separately scaled space avoids OCRmyPDF 17.4's selection running past the words; how pdf.js treats render mode 3 in extraction. veraPDF for `.notdef` (its license unread). *(survey, pdf images and writing; OCRmyPDF 17.x release notes)*

## For S0 (scan devices)

- **TEST-2** · sane-dl · S0 · open — **SANE in CI: the `test` and `pnm` backends, and the bindings against the header.** Built in S0 slice 1 and run here on SANE 1.4.0 (Ubuntu's `libsane1`, `libsane-dev` and `sane-utils`, 1.4.0-1ubuntu1): Ubuntu's `libsane1` has both backends; the `test` backend's hand-scanner mode gives `lines = -1` from its feeder too, on every sheet; and the header contract (sanetui's idea, Apache-2.0, in our own code) checks every constant, struct layout and function type of `sane_dl::ffi` against the installed `sane.h`, with a pass over the header's text for constants missing. CI's first run (2026-11-08, on the push of the slice's first step, before any of these tests existed) showed CI's SANE: `ubuntu-latest` is the `ubuntu-26.04` image, which installs `libsane1` and `libsane-dev` 1.4.0-1ubuntu1, the version here, and its `libsane1` holds both backends (the install step prints the versions, and fails naming a backend missing). What's left is CI's run of the tests, which waits on the push: the tests against those backends, which assert 1.4.0's behaviour (the pictures' sizes and solid values, the hand scanner from the feeder, the feeder's count running on across batches, the option layouts), any difference followed in the tests or moved to the fake, said; and the header contract against that `sane.h`. Close it once that run is green. If `ubuntu-latest` later moves to another sane-backends, its printed versions say so, and the require variables make a difference a failure, not a skip. *(survey, SANE and network scanning; S0 slice 1)*

- **TEST-3** · twain-dsm · S0 · open — **TWAIN's sample source on a hosted runner.** Whether `Twain_DS_sample01` (BSD-3) installs silently on `windows-latest` (`msiexec /qn`), or runs from yushulx/virtual-scanner's portable zip, or works with the DSM and the source copied into `twain_32` and `twain_64` (if the runner lets us write `C:\Windows\twain_*`); whether it scans with a hidden window in both bitnesses; `CAP_XFERCOUNT` from its environment variable sets the page count. *(survey, TWAIN, WIA and ICA)*

- **TEST-7** · sane-dl · S0 · open — **sane-dl against Homebrew's sane-backends on the macOS runner.** Untried: S0 slice 1 kept it out (its decision 18), so an unknown on a runner couldn't hold the slice; on macOS the tests that need libsane say they skipped. Try `brew install sane-backends` on `macos-latest`, then the tests with `SANE_DL_REQUIRE_LIBSANE=1` through an isolated `ConfigDir` naming `test`. Since S0 slice 1's code review `Sane::load()` tries absolute paths on macOS and no bare name (which dyld would also seek in the working directory, and whose fallback search holds `/usr/local/lib` for old binaries only): `/opt/homebrew/lib/libsane.1.dylib` (Homebrew on Apple silicon, as the runners are), `/usr/local/lib/libsane.1.dylib` (Homebrew on Intel), `/opt/local/lib/libsane.1.dylib` (MacPorts). The item says whether Homebrew installs the library under that name there, and whether `load()` opens it. Also: whether Homebrew's build has the `test` and `pnm` backends, and the header contract against its `sane.h` (`SANE_DL_SANE_H`). *(S0 slice 1, `crates/sane-dl.md`)*

- **TEST-8** · sane-dl, fake-libsane · S0 · open — **S0 slice 1's code on CI's Windows and macOS.** Built and checked on Linux, with clippy for both other targets; what only CI shows: the fake built as a DLL and a dylib by the tests' nested build and loaded by its path, rusty-fork's children on each, the abort's exit code on Windows (`0xC0000409`), the build script that builds nothing and the `links` key, the tests that need libsane or `sane.h` saying they skipped, and on macOS `load()` refused as `NotFound` naming its three paths (before TEST-7 installs Homebrew's SANE). Close it once CI's run of the slice's push or pull request is green on both. *(S0 slice 1, code review)*
