## For S0 (scan devices)

- **Q-4** · sane-dl, scan-device (`sane` backend) · S0 · open — **A SANE device's vendor, model and kind: its bytes, or lossy UTF-8?** The standard makes every SANE string Latin-1. `sane-dl` gives a device's name as its bytes (`DeviceName`, which the model's id reads as Latin-1) but its vendor, model and kind as UTF-8 with any other byte replaced, so a Latin-1 byte is lost (S0 slice 2's probe N1, through the fake: a vendor `Caf\xe9 Scan` came back with U+FFFD for the `\xe9`); the `test` and `pnm` backends send ASCII (`Noname`, `frontend-tester`, `PNM file reader`). The fallback by backend, vendor and model compares the stored device's strings with a fresh listing's, which match while both came through the same conversion; what's lost is the text shown, and a match across a `sane-dl` whose conversion changed. Settled by slice 5, before `sane-dl`'s first publish if its API changes: the three as bytes too (or read as Latin-1, as the id is), or kept as they are, from what backends are seen to send (the fi-6130's, TEST-9). *(S0 slice 2, probe N1; its plan's rejected finding 6)*
- **Q-5** · scan-device · S0 · open — **How the packaged crate's tests get the fake.** The crate's tests turn the `fake` feature on through a dev-dependency on the crate itself, a path alone (S0 slice 3's decision 6), and packaging drops a dev-dependency with no version: `cargo package` keeps `fake = []` and `rusty-fork` in the manifest but not that line, so from the package `fake_devices`, `fake_batches` and `fake_faults` don't build and the crate docs' example fails as a doctest (`E0432`, `scan_device::fake` unresolved), while the layout's tests pass (slice 3's step 4 probe, 2026-11-09). crates.io builds no tests, but a distribution that runs a crate's tests from its package would meet it. Options: `required-features = ["fake"]` on those test targets and the example's doctest marked to run only with the feature; `#![cfg(feature = "fake")]` atop each test file; or the package's docs saying its tests need `--features fake`. Settled by slice 11, which makes the crate ready to publish, in its package check. *(S0 slice 3, step 2's check and step 4's probe)*
- **Q-6** · scan-device · S0 · open — **What else of the model may grow, before it's frozen.** S0 slice 3's code review made `Paper` and the fake's `When` `#[non_exhaustive]` (its decision 42), since a variant added after 0.1.0 breaks every exhaustive match, slice 4's wire conversions among them. Still exhaustive: `Resolutions`, `Side` and `SideKnown`; plain structs with public fields that a caller writes as literals: `SizeMm`, `Encoded`, `Opened` (which every backend builds), `DeviceId` and `WindowOwner`. And `Copy` on the growing enums (`Status`, `Done`, `Driver`, `Source`, `Format`, `Encoding`, `EncodedKind`, `WindowClosed`, `Paper`, `When`): dropping it later breaks callers, keeping it holds every future variant to plain data. For each, kept (a side is front or back) or changed, said. Settled by slice 11, which freezes the model, after slices 4, 5, 9 and 10 have met it. *(S0 slice 3, its code review)*
- **Q-7** · sane-dl · S0 · waiting on review — **Refuse to load SANE where the loader's search path holds an empty or relative entry?** `Sane::load`'s safety rests on two rules of the process's environment (S0 slice 1a's code review, its decision 33): every entry of the loader's search path absolute, since glibc looks an empty or relative one up from the working directory as the library loads, which safe code can change; and `LD_LIBRARY_PATH`, `SHLIB_PATH` and `LIBPATH` never changed inside a process using SANE, since SANE's `dll` reads them as it loads each backend. Both are said in the docs, as the Vulkan loader's variables are under ash's and wgpu's safe entries; neither is checked. On Linux the first could be: the starting value is in `/proc/self/environ`, which `set_var` doesn't rewrite, and a load could refuse an empty or relative entry with a `LoadError` of its own, at the cost of refusing a common slip (`LD_LIBRARY_PATH=/opt/x:` where the variable was unset) whose hazard needs the program's own change of directory. The second can't be checked: `dll` reads the variable after `load` returns. Settled by the review of slice 1a, before `sane-dl`'s first publish: the docs alone, as now, or the check on Linux. *(S0 slice 1a, code review: the soundness lens)*
