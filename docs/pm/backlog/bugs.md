# Bugs: known wrong behaviour not yet fixed

IDs BUG-1 to BUG-7; the next new one is **BUG-8**. Format and rules: `README.md`.

BUG-1 to BUG-6 are in sheaf's code as it is cut, so each is fixed in the slice that moves its file, and the
harness's byte-for-byte check parts from sheaf there only, said in the slice (plan.md, "Standing rules").
Revised 2026-11-08 from the prior-art survey (`research/prior-art/README.md`, "To crates.md
and bugs.md").

## For S0 (scan devices)

- **BUG-7** · sane-dl · S0 · open — **`Image`'s derived `Debug` prints a page's every byte.** `Image` derives `Debug` over `data: Vec<u8>` (`sane-dl`'s `src/scan.rs`), and `Page`, which holds one, derives it too, so `{:?}` of a page (a log line, `dbg!`, an `assert_eq!` that fails) writes each byte as decimal text: hundreds of MB for a 600 dpi color page of about 100 MB. Write `Image`'s `Debug` by hand (its format, depth, size, stride, frames and the data's length, not the bytes) for the next alpha, said in the changelog; the model's `RawImage` and `Encoded` do the same (S0 slice 3). Not a defect the seam can't do without, so no code change in S0 slice 2; whichever slice next releases `sane-dl` (S0 slice 5, if it needs a change there) takes it. *(S0 slice 2, code review)*

## For S1 (pages)

- **BUG-1** · scan-image · S1 · open — **G4 encoding truncates images wider than 65,535 pixels.** `encode::g4` passes `w as u16` to `fax` 0.2's `encode_line` (`encode.rs:136`; the test helper's `decode_g4` casts the same, `:160-161`), while `/Columns` or the TIFF's `ImageWidth` keeps the true width, so the image decodes as garbage. A 600 dpi scan over 109 in wide is enough, and nothing in `io.rs` caps width. `fax` 0.3.0 (2026-07-13) takes `u32` widths, but its G4 encoder computes `a1 as i16 - b1 as i16`, which panics with overflow checks on (debug and test builds) whenever two positions straddle 32,767; release builds happen to give the right result (issue #30). The fix merged on 2026-11-05 (PR #31) and isn't on crates.io. Fix: `fax` 0.3.1 once released, or the merge commit pinned, or widths past 32,767 refused with a typed error until then; the crate's dimension caps cover the rest. Read back through hayro-ccitt, since `tiff`'s G4 reader refuses widths past 65,535. Checked by a black-and-white page 70,000 × 100 px round-tripping with overflow checks on (or refused, said). *(sheaf B24, `scratch/reference/sheaf/backlog/B24.md`; entry 38; survey, image codecs)*
- **BUG-2** · scan-image · S1 · open — **Fax TIFFs (CCITT Group 3, Modified Huffman) are refused.** tiff 0.11.3 decodes only `Fax4` among the fax compressions: `Fax3` (3) and `Huffman` (2) fail with `UnsupportedCompressionMethod` (`tiff-0.11.3/src/decoder/image.rs:604-620`), and `io.rs` has no fallback. Fax software's TIFFs (Class F) are G3. Fix: every CCITT strip, compressions 2, 3 and 4 alike, taken as raw bytes from `tiff`'s IFD (`FillOrder` and `T4Options` read by us) and decoded through one hayro-ccitt 0.5.0 adapter, shared with `pdf-images`; 0.5.0 covers G3 1D and 2D, EOLs whatever the flag says, byte-aligned rows (Modified Huffman), end of block and damaged lines. Don't wait on `tiff`: its `main` reads G3 1D only (PR #363, unreleased, `T4Options` never read) and its Modified Huffman PR #414 has sat unreviewed since 2026-09-04. Fixtures: libtiff run as a separate process (as image-tiff made its own, PR #369), plus libtiff's `fax2d.tif` and `g3test.tif`; nothing in Rust encodes G3 or MH. Triage with BUG-3. *(sheaf B25; entry 16; survey, image codecs)*
- **BUG-3** · scan-image · S1 · open — **Some TIFF kinds are refused: CMYK16, float RGB and RGBA, planar, two-sample gray.** `io::tiff_image` fails on them where image's `load` reads them, so in sheaf a scanned TIFF's first page reads (through `load`) and its later pages don't. `tiff` decodes them all: planar itself (`decoder/mod.rs:1147-1222`), two-sample gray as `Multiband { num_samples: 2 }` "for compatibility"; the refusals are the callers'. `image` 0.25.9 added initial 16-bit CMYK TIFF support. Fix: map each kind in `scan-image`, or name the kind refused. `tiff_image`'s `GrayA` arms are unreachable. Rare from scanners and fax software. *(sheaf B15, B25's notes; survey, image codecs)*
- **BUG-4** · scan-image · S1 · open — **A TIFF's Orientation tag is ignored by `tiff_pages`.** `io::load`, `decoded` and `frames` turn or mirror the image as the tag says; `tiff_pages` (behind sheaf's images-to-pdf, Combine and image inserts) doesn't, so the same file comes out differently scanned and inserted. Confirmed: `tiff` exposes the tag and never applies it, while `image`'s TIFF decoder maps it. Fix: the tag applied after decoding, as `frames` does for later pages, `tiff_pages`' output otherwise unchanged (its CMYK conversion is pinned). In the crate, every path to a page goes through one orientation step. Checked by a TIFF with Orientation 6 read by each path. *(sheaf B14; survey, image codecs)*
- **BUG-5** · scan-cleanup · S1 · open — **imageproc's Otsu threshold overflows on large images of one gray.** imageproc 0.27.0's `contrast::otsu_level` multiplies in `u32` (`threshold as u32 * hist_count`, `width * height`): once one gray level has more than 16,843,009 pixels it panics in debug builds and gives a wrong threshold in release. A blank 600 dpi Legal page is 42.8 million pixels. Called by `clean.rs:289` and `:466`, which M5 slice 3 saw called on reduced images only, without tracing every caller. Confirmed in 0.27.0's source; no issue is filed, and PR #740 (a float-precision change) was closed unmerged. Fix: a `u64` (or f64, as seiza-imgproc's OpenCV-exact port does) Otsu in `scan-cleanup`, a copy of the one `codes/patch.rs` already has (`patch-codes` and `scan-cleanup` don't depend on each other). `adaptive_threshold`'s `u32` integral image has the same kind of overflow once a page's total brightness passes 2³²; sheaf's cleanup doesn't call it, and it stays uncalled on full pages. Upstream: UP-1. *(sheaf B39; survey, page cleanup)*

## For S2 (PDF)

- **BUG-6** · pdf-scan · S2 · open — **The glyphless font's ToUnicode is one range across every high byte.** sheaf's `Glyphless` writes `1 beginbfrange <0000> <FFFF> <0000> endbfrange` (`sheaf-doc/src/content/font/glyphless.rs:40-42`). The range crosses 255 high-byte boundaries, which Chromium's PDF writer forbids (bfrange entries may not change the high byte), and Ghostscript 9.56 to 10.04.x discards a whole ToUnicode map when any block has more than 100 entries (OCRmyPDF's 17.x notes). Fix: 256 ranges, one per high byte, at most 100 to a block, about 7 KB more before compression. Checked by PDFium, pdf.js and Poppler extracting the same text (TEST-1), and by Ghostscript if it's in the matrix. *(survey, pdf images and writing; Chromium review 23519006)*
